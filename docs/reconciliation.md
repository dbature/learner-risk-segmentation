# Cross-module reconciliation (Final Project)

Before the integrated report was written, every commitment in Modules 1 and 2
was checked against what Modules 3 to 5 actually built and measured. Each
row records the contradiction and how it is resolved. Nothing here was
resolved by rewriting an earlier document: the earlier documents stay as
submitted, and this file is the record of what changed and why.

| # | Earlier commitment (source) | What actually happened | Resolution |
|---|---|---|---|
| 1 | Predict **withdrawal** (Module 1, Section 4; RAID R7) | Target switched to **non-completion** (withdraw or fail) by a rule fixed before tuning: switch if it beats withdrawal by 0.03 AUC. It did, 0.771 against 0.697 (`reports/target_check.json`). | Non-completion is the target everywhere downstream: model, dashboard, API, monitoring. |
| 2 | Recall at least **0.70** while flagging at most 25% (Module 1 goals; Module 2 objective) | 0.448 on the hold-out, 0.413 on a later course run. The target was set before learners who had already left were removed from the population (Module 3). | Reported as **missed**. Acceptance criteria reset against baselines in Module 4. Reaching 70% would need coaches to see about half the cohort (dashboard capacity curve). |
| 3 | IMD recall gap within 5 points (Module 1 goals and fairness objectives) | Literal max-min gap 13.9 points; a 10-band max-min rule fails a perfectly fair model about 99% of the time. Chi-square test of equal recall: p = 0.008, so the difference is real, in favour of the most deprived. | Many-level rule amended to a chi-square test, **pending Ethics Committee ratification**. The model fails it either way and stays in Staging. |
| 4 | Recall parity across disability within 5 points (Module 1) | 0.3 points before mitigation, 5.1 after the sex-specific thresholds. | Recorded as a gate **failure**, not rounded away. One of the three questions in the release review pack. |
| 5 | "DPIA completed before modelling" (Module 1 risk register; ticket #4; RAID D2) | Ticket #4 was never closed: no DPIA was approved before modelling. Modelling went ahead on an open-licence, already pseudonymised public dataset. | Disclosed as a process breach. The DPIA content is now in `docs/ethics/algorithmic_impact_assessment.md`, and the release review pack requires its approval before any use with real learners. |
| 6 | Ticket #23: "Sign off recorded before public deployment" (Module 2 board) | The dashboard and API were deployed publicly in Module 5 and the Final Project without a sign-off. | Distinguished explicitly: what is public is a **demonstrator** on open data with no real programme learners and a Staging model. **Operational release** to coaches still requires the sign-off. #23 stays open. |
| 7 | Split "GroupShuffleSplit on id_student" (RAID R3) | StratifiedGroupKFold on the HMAC-pseudonymised `learner_key`. The split therefore depends on the secret salt, which Module 4 discovered when two salts gave different test sets. | Documented in the model card. Production runs use one controlled salt; the monitoring replay uses the same split. |
| 8 | "Split indices versioned with DVC" (RAID D5) | Split is reproduced from seed + keys instead; DVC stages exist (`dvc.yaml`) but no DVC remote was set up. | Reproducibility shown in practice: three independent laptop runs reproduced the model, metrics and dashboard files exactly (Modules 4 and 5). DVC remote listed as an open implementation item. |
| 9 | Segments "steady, slipping, disengaged, **recovering**" (Module 1) | K-means on module-relative weekly activity gave steady, slipping, disengaged and **late starter**; no "dip then recover" group exists in four weeks of data. Silhouette 0.28. | Late starter reported as the nearest match; modest separation stated wherever segments appear. |
| 10 | Weekly ranked caseload with role-based views (Module 1 requirements) | Public dashboard holds aggregates only. The caseload ranks a cohort a coach uploads; nothing is stored. No login or role separation. | Role-based access is an implementation requirement for operational use (`docs/monitoring.md`, deployment plan). |
| 11 | "Flags expire weekly; no learner-visible score" (Module 1 risk register) | No learner-facing output exists, so the second holds. Weekly expiry is not implemented. | Added to the deployment plan: caseloads are regenerated each week and old flags are not carried forward. |
| 12 | Power BI organisational view (Module 1 stack) | Not built. Streamlit covers the cohort view. | Dropped from scope; noted as optional. |
| 13 | Adoption: 60% of flags actioned within a week (Module 1 goals) | Cannot be measured without a pilot. | Kept as a pilot KPI in the monitoring plan. |
| 14 | Airflow DAG (course continuity matrix) | Prefect flow (`flows/oulad_pipeline.py`). | Same role (orchestrated, retried, logged stages); choice justified in Module 3. |
| 15 | API top factors listed one-hot columns ("Module FFF") in Module 4 | The API now groups contributions into plain-language factors ("Which course they are on"), the same function the dashboard uses. Scores are unchanged (Learner A 0.8961). | One explanation function for API, dashboard and explanation store. |
| 16 | Dashboard dependencies resolved at deploy time | A newer pyarrow release requires NumPy 2 and would have broken the next redeploy. | `pyarrow==16.1.0` pinned in both Streamlit apps; the CI dashboard job installs exactly those files. |
